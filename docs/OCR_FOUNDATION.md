# OCR Foundation

Issue #62 / S3-006 adds a user-triggered OCR boundary for an existing private image Media.

## Public flow

```text
authenticated user
  -> POST /v1/media/{media_id}/ocr
  -> owner + READY + completed + IMAGE gate
  -> server-side private object read
  -> AIGateway image inference
  -> strict OCR JSON parser
  -> typed OCRResult (trust_class=inference)
```

The endpoint accepts only the opaque `media_id` from the route. Clients cannot provide an
object-storage key, public URL, provider endpoint, model name, API key, trust class, or
confidence value.

## Media privacy boundary

OCR is allowed only when all of these are true:

- the Media row belongs to the authenticated owner;
- the media state is `READY` and has a server completion timestamp;
- the media kind is `IMAGE`;
- the server-side final object still matches the recorded byte size;
- the image is within the existing server media size bound.

The OCR service reads the final object through the server's configured `ObjectStorage`.
It never trusts a client URL and never creates a public storage URL.

The database boundary is split into short phases: take and commit a stable owner/media
snapshot, perform storage/provider I/O without an open DB transaction, then re-lock and
revalidate the Media plus user-data deletion generation before returning the result.

The current provider image boundary accepts JPEG, PNG and WEBP. Existing HEIC/HEIF media
remains valid Media, but OCR fails closed until a trusted server-side conversion boundary
is implemented; bytes are never relabeled as another image type.

## AI Gateway boundary

Feature code does not call a model vendor directly. Image inference extends the existing
`AIGateway` contract:

- image bytes remain server-side;
- provider credentials remain server-side;
- input byte size and output-token limits are enforced;
- provider calls have a wall-clock timeout;
- provider/model/request provenance is retained;
- production provider requests use `store=false`;
- malformed, incomplete, failed and refused provider responses fail closed.

The deterministic provider has a separate image seam so service tests do not require
network access or vendor credentials.

## OCR output contract

The provider may return only:

```json
{
  "blocks": [
    {"text": "visible text"}
  ]
}
```

Unknown fields, malformed JSON, invalid block types, blank block text and excessive block
or text size are rejected. Block indexes and the combined `text` field are generated by
the server, not trusted from provider output.

An image with no visible text returns an explicit empty result:

```json
{"blocks": []}
```

There is no fabricated fallback text.

## Trust and persistence

OCR text is derived from image evidence and is always:

```text
trust_class = inference
```

S3-006 does **not** create or modify:

- Memory / MemorySource;
- Object / Place / Person;
- Visit;
- Reminder;
- Memory Pipeline Store state.

OCR output is returned to the caller only. A future Pipeline integration must separately
pass the existing Evidence and confirmation gates before anything can become a
query-answerable Memory.

Uploading or completing a photo never triggers OCR automatically. There is no photo
library scanner in this foundation.
