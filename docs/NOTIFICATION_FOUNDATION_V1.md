# NOTIFY-001A Server Notification Foundation V1

## Scope

NOTIFY-001A establishes server-side notification authority only. It does not add
Flutter/iOS/Android permission flows, live APNs credentials/network delivery, an Android
vendor decision, Admin React UI, reminder due-time delivery, read receipts, or human-open
tracking.

The canonical device identity remains `Device(user_id, client_uuid)`. Push state is an
extension of that row, not a competing PushDevice identity.

## Device push authority

A device becomes eligible only after authenticated registration through:

```text
PUT /v1/notifications/device
```

The authenticated session is the only source of `user_id`. The request supplies a bounded
`client_uuid`, reviewed `IOS|ANDROID` platform, reviewed provider, raw provider token,
and optional app/OS versions.

Durable push authority is:

```text
Device
  platform
  push_provider
  push_token              # server-only operational secret
  push_token_digest       # SHA-256 lookup/audit identity
  push_enabled
  push_token_updated_at
  push_invalidated_at
  app_version
  os_version
```

The same provider token may have only one active binding. PostgreSQL registration takes a
digest-scoped advisory transaction lock before retiring an old binding and activating the
new one, and the partial unique index is the final database invariant.

Provider disclosure and token ownership transition share a second
`provider + token_digest` session-level advisory handoff. Delivery acquires that handoff,
re-checks owner/provider/raw-token/digest/platform authority, closes the short database
transaction, performs provider I/O while only the session advisory handoff remains held,
then releases it. Rebind and unregister must acquire the same handoff before changing
ownership. A rebind therefore cannot complete while an old owner is still allowed to
disclose notification content to that token.

Re-registering the same owner/device/token is idempotent. Rotation atomically replaces the
token authority. Unregister clears active token authority without deleting the Device row
or unrelated device/location history:

```text
DELETE /v1/notifications/device/{client_uuid}
```

Logout/session revocation behavior is intentionally unchanged in 001A. NOTIFY-001B must
call this safe unregister seam when its reviewed client logout/token lifecycle requires it.

Legacy non-null `devices.push_token` values have no reviewed provider provenance.
Migration 0036 therefore clears the legacy raw token and leaves the device inactive until
it explicitly re-registers through the new API. The migration never invents IOS/ANDROID or
provider provenance.

## Canonical notification domain

`NotificationMessage` is provider-neutral immutable content and correlation authority.
Canonical push payload is generated by the server from a typed route contract:

```text
version = 1
destination = HOME | REMINDER | MEMORY | APP_UPDATE | FAMILY | EXPORT
resource_id = optional opaque UUID
```

Arbitrary provider JSON, URLs, coordinates, Memory content, tokens, signed URLs,
credentials and auth headers are not accepted as canonical payload fields.

Initial categories/source types are:

```text
REMINDER
ADMIN
SYSTEM
APP_UPDATE
EXPORT_COMPLETE
FAMILY
```

`NotificationCampaign` owns target selection, scheduling, fan-out revision and progress.
Explicit USER_IDS and DEVICE_IDS are normalized foreign-key target rows instead of raw ID
arrays in JSON.

`NotificationDelivery` is one logical campaign/device delivery and is unique on
`(campaign_id, device_id)`.

## Targeting and audience cutoff

Reviewed target dimensions are intentionally narrow:

```text
platform:
  ALL | IOS | ANDROID

audience:
  ALL_ELIGIBLE_DEVICES | USER_IDS | DEVICE_IDS
```

Eligibility requires an active reviewed push binding and excludes invalidated/no-token
devices and owners currently under Data Delete or Account Delete.

On submit, the campaign records `audience_cutoff_at`. Fan-out only admits devices whose
Device row and current push-token authority existed at or before that cutoff. A device
registered or rotated after the cutoff does not nondeterministically enter the campaign.
A token that changed after snapshot is also fenced at delivery time by the stored provider
and token-digest snapshot.

## Scheduling and Admin authority

The server exposes backend primitives for the later NOTIFY-001C console:

```text
POST /admin/api/v1/notifications/campaigns
GET  /admin/api/v1/notifications/campaigns/{id}/preview
POST /admin/api/v1/notifications/campaigns/{id}/submit
GET  /admin/api/v1/notifications/campaigns/{id}
POST /admin/api/v1/notifications/campaigns/{id}/cancel
```

SUPPORT_READONLY can read but cannot mutate. SUPER_ADMIN and OPERATOR mutations reuse the
existing Admin CSRF/session guard.

Creation is always DRAFT. Preview returns eligible total/iOS/Android counts plus a
server-HMAC confirmation token bound to campaign revision and target definition. Submit
must present both the expected revision and that confirmation token; a single accidental
POST cannot fan out a bulk campaign.

`send_at` is stored/executed in UTC. Past scheduling is rejected. Create, immediate send,
schedule and cancel produce AdminAudit entries without raw push tokens.

Cancellation fences future fan-out and changes PENDING/RETRY_WAIT delivery rows to
CANCELLED. An already in-flight provider request is not falsely described as recallable.
FAILED, COMPLETED and CANCELLED campaigns are final and reject later cancel mutations with
`NOTIFICATION_CAMPAIGN_FINAL`; historical failure cannot be rewritten as administrator
cancellation.

## Durable execution

OPS-002 remains the only queue/worker framework:

```text
NOTIFICATION_FANOUT
NOTIFICATION_DELIVERY
```

Fan-out uses a bounded Device UUID keyset page, durable campaign cursor, campaign revision,
audience cutoff and one logical delivery per campaign/device. Each committed page creates
its delivery rows and durable delivery jobs in the same transaction. Crash/reclaim or even
duplicate fan-out authority cannot create duplicate logical delivery rows.

Delivery attempt authority is:

```text
PENDING
→ RUNNING (revision++, random attempt_token)
→ ACCEPTED
   RETRY_WAIT
   TERMINAL_FAILURE
   CANCELLED
   EXPIRED
```

Provider I/O occurs only after RUNNING attempt authority is committed and the disclosure
handoff has re-confirmed the current Device binding. Finalization requires the exact
revision and attempt token, so stale attempts cannot overwrite newer/terminal state.
Provider errors are mapped to bounded internal codes. Raw provider response/error text is
not persisted.

OPS-002 terminal maintenance failure is also part of the public authority contract:
a final delivery-job crash converges the delivery to TERMINAL_FAILURE and clears any active
attempt token; a final fan-out-job failure marks the campaign FAILED with a bounded error
code. Non-final raw delivery failure is fenced into RETRY_WAIT. A maintenance terminal state
therefore cannot leave notification state stuck indefinitely in RUNNING/FANOUT.

`ACCEPTED` means the provider accepted the request; it is not proof of human receipt/read.

## Provider phase boundary

The 001A adapter interface is provider-neutral. A deterministic TEST adapter exists only in
non-production tests. APNS/FCM/HMS values reserve reviewed routing provenance but have no
live network adapter in 001A.

Production resolves unconfigured live providers to a terminal bounded failure and can
never mark a notification ACCEPTED merely because the durable queue ran successfully.
Live provider/client integration belongs to NOTIFY-001B.

## Privacy, deletion and export

Raw push tokens are operational secrets:

- never included in notification MaintenanceJob payloads;
- never returned by Device/Admin notification APIs;
- never used as observability correlation keys;
- never serialized by Data Export;
- provider exception text/body is not persisted.

001A does **not** create user-visible notification history. Campaign/message rows are
Admin/control-plane state. Per-device `NotificationDelivery` is operational user-linked
state and is explicitly included in Data Delete inventory/deletion.

Account Delete converges through the existing Data Delete/Device/User cascade: deleting the
owner removes Device push authority, normalized user/device targets and delivery rows.
Foreign-key serialization plus delivery-time Device token-digest fencing prevents fan-out
from resurrecting delivery authority for a deleted account.

## Review gates

Focused CI covers device lifecycle, rebind, targeting, Admin confirmation/scheduling,
bounded multi-page fan-out, provider result state transitions, stale-attempt fencing, TTL,
redaction and export exclusion.

The real PostgreSQL gate additionally proves:

- legacy unqualified token migration is inactive;
- concurrent shared-token rebind leaves exactly one active authority;
- two worker fan-out authority is serialized with unique logical deliveries;
- stale PostgreSQL delivery attempts cannot overwrite accepted state;
- final account-delete cascade racing fan-out leaves no victim Device/delivery authority.

Schema drift and the full backend suite remain mandatory. No `mobile/**`,
`miniprogram/**`, Admin visual UI or Golden files are changed in NOTIFY-001A.
