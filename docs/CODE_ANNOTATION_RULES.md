# 代码人工注释标记规范

## 目的

从本规范生效后，所有**人工维护的新增代码或修改代码**都要带明确的人工注释标记，方便代码审查时快速定位“本次为什么改、对应哪个开发任务”。

统一关键字：

`[人工注释]`

建议同时带开发进度 ID，例如：

`[人工注释][S1-009]`

---

## 各语言写法

### Python / YAML / Shell / TOML

```python
# [人工注释][FND-007] 查询个人事实前必须验证真实 Evidence，禁止仅凭 confidence 回答。
```

### Dart / TypeScript / JavaScript / Kotlin / Swift / Java / C / C++

```dart
// [人工注释][S1-013] 问记忆页面只展示服务端证据化结果，不在客户端自行推断答案。
```

### SQL

```sql
-- [人工注释][FND-011] 保证同一个 object 最多存在一条 CURRENT 位置记录。
```

### HTML / Markdown

```html
<!-- [人工注释][DOC-PROGRESS-001] 开发进度状态说明。 -->
```

---

## 新建代码文件规则

人工新建的源码文件，在文件顶部或第一个核心逻辑块前增加一条说明，例如：

```python
# [人工注释][S1-007] 新增 ASR 服务入口，负责把用户主动上传的语音转换为文本证据。
```

注释必须说明：

1. 为什么新增；
2. 对应哪个开发进度 ID；
3. 关键安全/业务不变量（如果存在）。

---

## 修改现有代码规则

修改已有源码时，应把标记放在**发生语义变化的逻辑块附近**，而不是只写在文件顶部。

推荐：

```python
# [人工注释][FND-016] recorded_at 落在历史暂停区间时永久拒绝，防止恢复后延迟补传绕过隐私暂停。
if pause_history.contains(recorded_at):
    ...
```

不推荐：

```python
# [人工注释] 修改了一些代码
```

注释必须能够让审查者不读 PR 描述也基本知道这段逻辑为什么存在。

---

## 不允许的做法

1. 不要给每一行重复添加 `[人工注释]`，只标记一个完整逻辑块。
2. 不要用注释替代测试。
3. 不要为了添加注释修改标准生成文件格式。
4. 不要在注释中写 Token、密钥、个人隐私或真实用户敏感信息。
5. 不要用“临时”“先这样”等模糊文字替代技术原因。

---

## 特殊文件例外

下列文件原则上**不强行写入注释**，否则可能破坏格式或造成无意义 diff：

- `package-lock.json`
- `pubspec.lock`
- 二进制图片 / App Icon
- Flutter / Xcode / Gradle 自动生成且不适合人工维护的文件
- 严格 JSON 配置（JSON 标准不支持注释）
- 第三方 vendor / generated 文件

这类文件如果因任务发生变化，必须通过以下方式追踪：

- commit message；
- PR 描述；
- `docs/DEVELOPMENT_PROGRESS.md` 对应任务 ID。

如果 JSON schema 明确允许说明字段，也不能为了“加注释”擅自加入未知字段。

---

## 审查规则

以后审查新增/修改代码时，同时检查：

- 是否有对应的开发进度 ID；
- 是否有 `[人工注释][任务ID]`；
- 注释是否说明了业务原因而非复述代码；
- 安全、隐私、可信记忆等关键不变量是否有明确注释；
- 自动生成文件是否正确使用了例外规则。

如果缺少上述标记，可作为代码规范问题要求补充后再合并。
