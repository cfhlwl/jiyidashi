# 代码开发注释规范

## 目的

代码注释的目标是帮助维护者和审查者理解**这段代码为什么存在、保护了什么约束、哪些边界不能破坏**。

不要求固定标签，也不要求为每次修改机械添加注释。任务归属与开发进度由 Issue、PR、commit 和 `docs/DEVELOPMENT_PROGRESS.md` 追踪。

---

## 什么时候应该写注释

以下情况应优先写正常开发注释：

1. 业务意图仅从代码表面不容易看出来；
2. 涉及隐私、安全、Evidence、fail-closed 或权限边界；
3. 涉及并发、事务、幂等、重试、锁、时间水位等容易被以后“优化坏”的逻辑；
4. 存在平台限制、兼容性限制或特殊生命周期；
5. 某个实现看似可以简化，但实际上必须维持当前写法；
6. 重要测试 seam、故障注入或回归保护需要解释测试职责。

简单赋值、明显的 getter/setter、常规 UI 布局等自解释代码，不需要为了数量而加注释。

---

## 好注释的写法

### Python

```python
# 业务资源与幂等账本必须在同一事务提交；
# 唯一键竞争失败后整体 rollback，避免留下重复 Memory/Evidence。
db.commit()
```

### Dart

```dart
// recorded_at 在首次入队时冻结，保证延迟同步不会把旧位置
// 伪装成“现在发生”的位置并越过 UNKNOWN 水位。
final recordedAt = now.toUtc();
```

### SQL

```sql
-- 每个 Object 最多只能存在一条 CURRENT 位置记录，
-- 数据库约束是应用层锁之外的最终一致性保护。
CREATE UNIQUE INDEX ...
```

注释应尽量解释“为什么”和“不变量”，不要只是把下一行代码翻译成中文。

---

## 新建代码文件

人工新建的重要源码文件，应在模块入口、核心类型或关键逻辑附近解释：

- 该模块负责什么；
- 与现有模块的边界是什么；
- 有哪些重要安全、可信或一致性约束。

不要求在文件顶部放统一格式的任务标签。

---

## 修改现有代码

修改已有源码时，只在**真正发生语义变化且需要解释**的位置补充或更新注释。

推荐：

```python
# 暂停区间是历史隐私水位；即使用户已经恢复记录，
# 落在历史暂停区间内的延迟数据也必须永久拒绝。
if pause_history.contains(recorded_at):
    ...
```

不推荐：

```python
# 修改暂停逻辑
if pause_history.contains(recorded_at):
    ...
```

---

## 不允许的做法

1. 不要给每个代码块机械添加固定格式标签；
2. 不要用注释复述显而易见的代码；
3. 不要用注释替代测试、类型约束或数据库约束；
4. 不要为了满足注释要求修改 generated/lockfile/二进制文件格式；
5. 不要在注释中写 Token、密钥、真实用户隐私或其他敏感信息；
6. 不要用“临时”“先这样”等模糊文字代替真实技术原因。

---

## 特殊文件

以下文件通常不要求人工注释：

- lockfile；
- 二进制图片、字体和 App Icon；
- Flutter / Xcode / Gradle 等自动生成文件；
- 严格 JSON 配置；
- 第三方 vendor / generated 文件。

这些文件的任务归属通过 commit、PR 和开发进度表追踪。

---

## 软件著作权准备 / Annotation Gate

此 Gate 是长期维护与软件著作权材料准备的代码质量门禁，**不是注释数量考核**。PR 只要新增或修改人工维护源码，审查者都应确认以下项目：

1. 重要新模块在模块入口、核心类型或关键逻辑附近说明**职责与边界**；
2. 隐私、安全、认证、Evidence、fail-closed 等逻辑说明必须长期保持的**可信不变量**；
3. 并发、事务、锁、幂等、重试、时间水位等逻辑说明**为什么不能被表面简化**；
4. 生命周期、权限与 Android/iOS/微信等平台差异说明**平台约束和状态所有权**；
5. 注释必须与当前实现一致；实现变化导致旧注释失真时，必须在同一 PR 更新；
6. 禁止“把下一行代码翻译成中文”的机械注释，也禁止为了软著材料堆砌无维护价值的注释；
7. generated、第三方、lockfile、图片、字体、图标和其他非人工维护文件保持原样，不为 Gate 人为改写；
8. Gate 不替代测试、类型、数据库约束或正式审查；涉及关键不变量时仍必须有可执行回归保护。

审查结论应明确回答：**关键职责是否可理解、边界是否可维护、注释是否真实、是否存在噪声或过期说明**。缺少必要说明可以作为代码质量问题阻塞合并；没有固定标签或固定注释模板不构成问题。

## 审查规则

以后审查新增/修改代码时，重点检查：

- 关键逻辑是否有足够的意图说明；
- 隐私、安全、可信记忆、并发、事务、幂等和失败语义是否明确；
- 注释是否与当前代码一致；
- 是否存在为了“有注释”而产生的噪声；
- generated 文件是否保持原生格式；
- 任务是否已经在进度表 / Issue / PR 中正确追踪。

缺少**必要的解释性注释**可以作为代码质量问题要求补充；缺少固定格式标签不再构成问题。
